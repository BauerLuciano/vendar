## 2. Decisiones de diseño

1. La intención durable es `SuscripcionPagoIntencion`.
2. `comercios.pending_intent_id` es el puntero autoritativo de la intención vigente.
3. `payments.pending_intent_id` vincula el pago con la intención.
4. La correlación de mismo comercio se garantiza con claves foráneas compuestas, no con trigger.
5. `conciliation_status` describe la correlación con la suscripción:
   - `aplicado`
   - `superseded`
   - `pendiente_conciliacion`
6. `reversal_status` describe el dinero reversado:
   - `sin_reverso`
   - `reembolso_parcial`
   - `reembolso_total`
   - `contracargo`
   - `reverso_combinado`
   - `desconocido`
   - `reversal_overlap_status` describe si el total combinado está informado o si el solapamiento es desconocido.
7. Un pago puede ser `aplicado` y, a la vez, tener un reverso. Sigue siendo una renovación aplicada, pero el dinero neto recibido se reduce cuando el reverso está confirmado; si el solapamiento es desconocido, el neto queda parcial y con cotas.
8. Un `superseded` no cuenta como renovación ni ingreso aplicado, pero sí aparece en el dinero bruto recibido y en el neto si corresponde.
9. No se cancelan preferencias remotamente en Mercado Pago. Se invalidan localmente y los pagos tardíos se rechazan o se registran para conciliación.
10. No se automatizan reversos de suscripción en B3.2. Un reembolso o contracargo se registra y se muestra, pero no cambia plan, vencimiento ni estado del comercio.
11. Los importes monetarios del camino de suscripción no se representan con `float`. Se usa `App\Support\ImporteDecimal`, con formato canónico de 2 decimales y aritmética en unidades menores. La compatibilidad legacy de ventas/pedidos conserva `?float` y queda fuera de B3.2.
12. `transaction_amount_refunded` es un snapshot acumulativo del total reembolsado. El importe de contracargo, si existe, se trata como snapshot del total contracargado. Reembolso y contracargo no se suman si el solapamiento es desconocido.
13. Los payloads de huérfanos no se guardan crudos. Se persiste una allowlist sanitizada y cifrada, más un hash SHA-256 del payload crudo para integridad y deduplicación.
14. La resolución de huérfanos se define como contrato de servicio, sin UI ni rutas en B3.2. La operación vincula o crea el pago, no aplica la suscripción.
15. La creación de pagos y huérfanos se serializa con un advisory lock transaccional por `provider + gateway_transaction_id`, para evitar que una carrera cree un pago y un huérfano del mismo movimiento.

#### 3.3.4. Unicidad de transacciones del proveedor

- Columna que almacena el ID de transacción: `payments.gateway_transaction_id` (`string`, nullable).
- Columna que identifica el proveedor: `payments.provider` (`string`).
- Proveedores usados:
  - `mercadopago` para suscripción online.
  - `manual` para pago manual.
  - `viumi` para pagos de pedidos web.
- Restricción: `UNIQUE (provider, gateway_transaction_id)`, nombre `payments_provider_tx_unique`.
- Modelo: `App\Models\Payment` ya expone `provider` y `gateway_transaction_id` en `$fillable`; D09 prueba el modelo contra la migración real.
- Migración original: `database/migrations/2026_06_14_000004_create_payments_table.php`.
- La migración `add_pending_intent_and_conciliation_to_payments_table` verifica que la restricción exista y la crea si falta, para recuperación ante migraciones parciales. Antes de crearla cuenta duplicados de `(provider, gateway_transaction_id)` no nulos; si existen, aborta con el detalle y no borra ni reasigna pagos. La resolución de duplicados es manual.
- PostgreSQL permite múltiples `NULL` en un unique. Por eso los pagos manuales con `gateway_transaction_id = NULL` no colisionan.
- Para pagos online de suscripción, `gateway_transaction_id` debe ser no nulo. Esa obligatoriedad la valida el servicio, no un CHECK global, porque los pagos manuales y otros proveedores pueden usar `NULL`.

Si el identificador ya pertenece a otro comercio:

1. La restricción unique impide crear una segunda fila.
2. El servicio busca el pago existente por `provider + gateway_transaction_id`.
3. Si pertenece al mismo comercio y está `aplicado`: respuesta idempotente `ya_aplicado`.
4. Si pertenece al mismo comercio y está `superseded` o `pendiente_conciliacion`: no se aplica; se informa conciliación.
5. Si pertenece a otro comercio:
   - No se modifica ninguno de los dos comercios.
   - No se reasigna el pago.
   - Se registra un incidente crítico con ambos `comercio_id`.
   - Se crea un `PagoHuerfano` con `motivo = conflicto_comercio` y `resolved_comercio_id = NULL`.
   - El webhook responde `200` con `status = conflict` para evitar reintentos masivos.
   - El caso queda visible para conciliación manual.

#### 3.3.5. Coherencia de períodos y conciliación

CHECK de PostgreSQL:

```sql
CHECK (
  CASE
    WHEN conciliation_status IS NULL THEN
      period_start IS NULL AND period_end IS NULL
    WHEN conciliation_status = 'aplicado' THEN
      period_start IS NOT NULL AND period_end IS NOT NULL
    WHEN conciliation_status IN ('superseded','pendiente_conciliacion') THEN
      period_start IS NULL AND period_end IS NULL
    ELSE false
  END
);

CHECK (
  period_start IS NULL
  OR period_end IS NULL
  OR period_start <= period_end
);

CHECK (
  conciliation_status IS DISTINCT FROM 'aplicado'
  OR COALESCE(status, '') IN ('approved', 'refunded')
);

CHECK (
  COALESCE(payable_type, '') = 'App\Models\Comercio'
  OR conciliation_status IS NULL
);
```

Validaciones del servicio:

- `aplicado` sólo se asigna después de validar token, puntero, estado, importe, moneda y preferencia.
- `period_start` y `period_end` se calculan con `SuscripcionService::calcularPeriodo`.
- `period_start <= period_end` se valida también en el servicio antes de persistir.
- `superseded` y `pendiente_conciliacion` se crean con períodos `NULL`.
- Pagos de ventas y pedidos conservan `conciliation_status = NULL` y no se tocan.
- El servicio no confía en que el CHECK reemplace las validaciones de negocio.

#### 3.3.6. CHECK de reversos

```sql
CHECK (refunded_amount IS NULL OR refunded_amount >= 0);
CHECK (chargeback_amount IS NULL OR chargeback_amount >= 0);
CHECK (reversed_amount_total IS NULL OR reversed_amount_total >= 0);

-- Se valida cada importe contra el total, no la suma.
-- Reembolso y contracargo pueden solaparse; la suma puede superar el importe.
CHECK (amount IS NULL OR refunded_amount IS NULL OR refunded_amount <= amount);
CHECK (amount IS NULL OR chargeback_amount IS NULL OR chargeback_amount <= amount);
CHECK (amount IS NULL OR reversed_amount_total IS NULL OR reversed_amount_total <= amount);

CHECK (
  reversed_amount_total IS NULL
  OR reversed_amount_total >= GREATEST(
    COALESCE(refunded_amount, 0),
    COALESCE(chargeback_amount, 0)
  )
);
CHECK (
  reversed_amount_total IS NULL
  OR reversed_amount_total <=
    COALESCE(refunded_amount, 0) + COALESCE(chargeback_amount, 0)
);

CHECK (
  reversal_status IS NULL
  OR reversal_status IN (
    'sin_reverso','reembolso_parcial','reembolso_total',
    'contracargo','reverso_combinado','desconocido'
  )
);
CHECK (
  reversal_status IS NOT NULL
  OR (
    refunded_amount IS NULL
    AND chargeback_amount IS NULL
    AND reversed_amount_total IS NULL
    AND reversal_overlap_status IS NULL
  )
);
CHECK (
  reversal_overlap_status IS NULL
  OR reversal_overlap_status IN (
    'no_aplica','total_combinado_informado','solapamiento_desconocido'
  )
);
CHECK (
  reversal_status <> 'sin_reverso'
  OR (
    refunded_amount IS NOT NULL
    AND refunded_amount = 0.00
    AND chargeback_amount IS NOT NULL
    AND chargeback_amount = 0.00
    AND reversed_amount_total IS NOT NULL
    AND reversed_amount_total = 0.00
    AND reversal_overlap_status = 'no_aplica'
  )
);
CHECK (
  reversal_status NOT IN ('reembolso_parcial','reembolso_total')
  OR (
    refunded_amount IS NOT NULL
    AND refunded_amount > 0
    AND chargeback_amount IS NOT NULL
    AND chargeback_amount = 0.00
  )
);
CHECK (
  reversal_status NOT IN ('reembolso_parcial','reembolso_total')
  OR amount IS NOT NULL
);
CHECK (
  reversal_status <> 'reembolso_parcial'
  OR amount IS NULL
  OR (refunded_amount IS NOT NULL AND refunded_amount < amount)
);
CHECK (
  reversal_status <> 'reembolso_total'
  OR amount IS NULL
  OR (refunded_amount IS NOT NULL AND refunded_amount = amount)
);
CHECK (
  reversal_status <> 'contracargo'
  OR (
    chargeback_amount IS NOT NULL
    AND chargeback_amount > 0
    AND refunded_amount IS NOT NULL
    AND refunded_amount = 0.00
  )
);
CHECK (
  reversal_status NOT IN ('reembolso_parcial','reembolso_total','contracargo')
  OR (
    COALESCE(reversal_overlap_status, '') = 'no_aplica'
    AND reversed_amount_total IS NOT NULL
  )
);
CHECK (
  reversal_status <> 'reverso_combinado'
  OR (
    COALESCE(refunded_amount, 0) > 0
    AND COALESCE(chargeback_amount, 0) > 0
    AND reversal_overlap_status IS NOT NULL
  )
);
CHECK (
  reversal_status <> 'desconocido'
  OR (
    reversed_amount_total IS NULL
    AND (
      reversal_overlap_status IS NULL
      OR reversal_overlap_status = 'solapamiento_desconocido'
    )
  )
);
CHECK (
  reversal_status <> 'desconocido'
  OR refunded_amount IS NULL
  OR chargeback_amount IS NULL
  OR refunded_amount = 0.00
  OR chargeback_amount = 0.00
);
CHECK (
  reversal_overlap_status <> 'no_aplica'
  OR COALESCE(refunded_amount, 0) = 0
  OR COALESCE(chargeback_amount, 0) = 0
);
CHECK (
  reversal_overlap_status <> 'total_combinado_informado'
  OR (
    refunded_amount IS NOT NULL
    AND chargeback_amount IS NOT NULL
    AND refunded_amount > 0
    AND chargeback_amount > 0
    AND reversed_amount_total IS NOT NULL
  )
);
CHECK (
  reversal_overlap_status <> 'solapamiento_desconocido'
  OR (
    refunded_amount IS NOT NULL
    AND chargeback_amount IS NOT NULL
    AND refunded_amount > 0
    AND chargeback_amount > 0
    AND reversed_amount_total IS NULL
  )
);
```

Los CHECK no reemplazan la validación del servicio. El servicio además rechaza snapshots con más de 2 decimales, fuera de rango, negativos o inconsistentes con el estado del gateway.

- `CHECK` de reversos equivalente al de `payments`, incluyendo `reversed_amount_total` y `reversal_overlap_status`.
- Índices por `resolved_comercio_id`, `resolved_intent_id`, `resolved_at`, `payload_purge_after`.
- Al crear un huérfano `approved`, si el gateway informa explícitamente ausencia de reverso (`0.00`), se usa `sin_reverso` con `0.00`; si falta el dato, `reversal_status = 'desconocido'` y montos `NULL`. Un huérfano `refunded`/`charged_back` con importes conocidos en `0.00` no se clasifica `sin_reverso`: queda `desconocido` y se registra incidente. No se asume cero.
- `payload_sanitizado` y `webhook_payload_sanitizado` son columnas `text` con cast `encrypted:array`; no son `jsonb` consultables.
- `payload_purge_after` se calcula al crear o resolver; `payload_purged_at` sólo lo setea la purga.

#### 3.4.1. Payload permitido, redacción, protección, acceso y retención

No se guarda el payload completo. Se guarda una allowlist mínima, cifrada, más un hash no reversible.

Campos permitidos del pago (`GET /v1/payments/{id}`):

- `id`, `status`, `status_detail`, `transaction_amount`, `currency_id`.
- `date_created`, `date_approved`, `date_last_updated`.
- `payment_method_id`, `payment_type_id`, `operation_type`.
- `external_reference`, `preference_id`, `live_mode`, `installments`.
- `transaction_amount_refunded`.
- De `metadata`, sólo las claves `tipo`, `plan_id`, `intencion_id` si existen y no contienen datos personales.

Campos permitidos del webhook:

- `id`, `type`, `action`, `data.id`, `live_mode`, `date_created`.

Se eliminan antes de persistir:

- Todo `payer`: email, nombre, apellido, identificación, teléfono, dirección, `payer.id`, tipo de persona.
- Todo `card`, `authorization_code`, datos de tarjeta, bin, últimos dígitos y titular.
- `additional_info`, `shipments`, `description`, `statement_descriptor`, `notification_url`, `callback_url`.
- `token`, `client_id`, `client_secret`, `access_token`, `refresh_token`, `signature`, `x-signature`.
- Headers, cookies, query strings completos y cualquier secreto de infraestructura.
- Cualquier campo no listado explícitamente. No hay fallback al payload crudo.

Protección:

- `payload_sanitizado` y `webhook_payload_sanitizado` se cifran en la aplicación con `encrypted:array`; la clave vive en el secret manager/entorno, nunca en la base.
- `payload_hash = SHA-256(raw_body)` del body que originó el registro (GET si existe; si no, webhook) se guarda para integridad y deduplicación. No se recalcula al actualizar, no es reversible y no contiene PII.
- Los payloads no se escriben en logs, cache, colas, correos ni reportes. Los logs sólo incluyen `provider`, `gateway_transaction_id`, `payload_hash` y `motivo`.
- B3.2 no escribe el body crudo de Mercado Pago en `payments.gateway_response` ni `payments.gateway_request` para pagos de suscripción; usa `PaymentStatusResponse` y campos allowlisted. Los pagos de ventas/pedidos conservan su comportamiento actual y quedan fuera de alcance.
- Los backups de PostgreSQL se cifran y tienen acceso restringido.
- La UI futura no muestra el payload crudo; sólo campos allowlisted y, si hace falta, `external_reference` completo para un admin autorizado.

Acceso:

- `pagos.huerfanos.ver`: permite ver metadatos y payload sanitizado. Sólo rol admin global.
- `pagos.huerfanos.resolver`: permite resolver. Sólo rol admin global.
- Los permisos se crean con `firstOrCreate` en `database/seeders/RoleSeeder.php` y se asignan a `Administrador Global`; no se asignan a roles de comercio. El despliegue ejecuta ese seeder idempotente; no se crean permisos en migraciones.
- Ningún usuario de comercio, API pública ni ruta de comercio puede leer `pagos_huerfanos`.
- Cada lectura o escritura de payload se audita con `activity()`: usuario, `huerfano_id`, acción y timestamp. No se registra el payload ni PII en la auditoría.
- No se permiten exportaciones masivas de payloads.

Retención y eliminación:

- Huérfano pendiente: payload sanitizado se conserva hasta 180 días desde `received_at`; luego se purga aunque siga pendiente. La resolución puede re-consultar el pago al proveedor.
- Huérfano resuelto: payload sanitizado se conserva 90 días desde `resolved_at`; luego se purga.
- Los plazos 180/90 son valores por defecto de `config/vendar.php` (`pagos_huerfanos.retention_pending_days` y `pagos_huerfanos.retention_resolved_days`). El comando de purga calcula el vencimiento con la configuración vigente y actualiza `payload_purge_after` si difiere; un cambio de plazo aplica sin migración.
- La purga setea `payload_sanitizado = NULL`, `webhook_payload_sanitizado = NULL` y `payload_purged_at = now()`. No borra `payload_hash`, `resolved_*`, `resolution_reason`, `resolution_note` ni la auditoría.
- `payload_hash` y los campos estructurados de resolución (`resolved_*`, `resolution_reason`) se conservan con el huérfano para auditoría; no contienen PII. `resolution_note` es texto operativo y no se replica en logs ni auditoría.
- Después de `payload_purged_at`, una notificación posterior no vuelve a guardar payload; sólo actualiza estado/reverso y auditoría.
- La purga se ejecuta con `App\Console\Commands\PurgarPagosHuerfanos` y es idempotente. No elimina pagos, huérfanos ni registros de auditoría.

Protección ante duplicados:

- Antes de crear un pago, se busca un huérfano no resuelto por `provider + gateway_transaction_id`; si existe, no se crea un segundo registro.
- Antes de crear un huérfano, se busca un pago por `provider + gateway_transaction_id`; si es de suscripción del mismo comercio, se actualiza; si es de otro comercio, se crea/actualiza el huérfano de conflicto; si es de otro dominio, se registra incidente y no se crea huérfano.
- `firstOrCreate` o `INSERT ... ON CONFLICT DO NOTHING`.
- Si ya existe, se incrementa `notification_count` y se actualiza `last_received_at`.
- No se sobrescribe `payload_sanitizado` con un payload distinto. Si el body de una notificación posterior produce un hash distinto, no se reemplaza `payload_hash`; se actualizan estado/reverso del huérfano y se registra el hash nuevo en la auditoría, conservando el payload y el hash originales.
- Si el pago ya fue resuelto, una notificación duplicada no lo reabre; si trae un reverso nuevo, se enruta al pago vinculado para actualizar su reverso, sin reabrir el huérfano.

Aislamiento:

- La tabla no tiene `comercio_id` inicial porque el comercio es desconocido.
- No se expone en rutas de comercio. Sólo admin global con los permisos anteriores.
- Si se expone en UI, se filtra por `resolved_comercio_id` y se muestran sólo campos allowlisted.
- El payload crudo no se guarda en ningún caso; sólo la versión sanitizada, cifrada, y su hash.

## 5. Flujos y concurrencia

### 5.1. Creación de intención y preferencia

`SuscripcionPagoService::crearIntencion()`:

1. Valida plan y origen.
2. Abre transacción.
3. Bloquea el comercio con `lockForUpdate`.
4. Busca intención `pendiente` vigente.
   - Si existe y está vigente: `409` con `checkout_url` para reanudar.
   - Si existe pero está expirada: la marca `expirada`, limpia el puntero si coincide y continúa.
5. Crea la intención con token único, plan, importe, moneda, `expires_at` y estado `pendiente`.
6. Actualiza en la misma transacción:
   - `comercios.pending_intent_id = intencion.id`
   - `comercios.pending_plan_id = plan.id`
7. Commit.
8. Crea la preferencia en MP con `external_reference = token` y metadata.
9. **Después de la respuesta HTTP**, abre una nueva transacción:
   - Bloquea el comercio.
   - Bloquea la intención.
   - Verifica que la intención siga `pendiente`.
   - Verifica que `comercios.pending_intent_id` siga apuntando a ella.
   - Si sigue vigente: guarda `preference_id` y `checkout_url`.
   - Si fue invalidada, reemplazada o aprobada: **no guarda ni publica la preferencia como vigente, no reactiva la intención y no toca el puntero**.
10. Si MP falla antes de la respuesta: marca la intención `invalidada`, motivo `error_pasarela`, y limpia el puntero si coincide.
11. Si la preferencia se creó pero la intención dejó de ser vigente: se registra un log con `preference_id` e `intencion_id` para auditoría. La preferencia remota no se cancela; su token ya está invalidado y cualquier pago será `superseded` o `pendiente_conciliacion`.

La llamada HTTP a MP queda fuera de la transacción para no mantener locks largos.

### 5.2. Respuesta cuando existe una intención pendiente sin preferencia creada

Caso: intención `pendiente`, `preference_id = NULL`, `checkout_url = NULL`.

- Si `updated_at` está dentro de la ventana de creación (`preferencia_timeout_segundos`, por defecto 30):
  - Responder `409`.
  - `estado = 'creando_preferencia'`.
  - `intencion_id`, `plan_id`, `expira_en_minutos`.
  - `checkout_url = NULL`.
  - `retry_after = 5`.
  - No crear una segunda preferencia.
- Si `updated_at` supera la ventana:
  - Invalidar la intención con motivo `timeout_preferencia`.
  - Limpiar el puntero si coincide.
  - Crear una nueva intención.
- Si `checkout_url` existe:
  - Responder `409` con `estado = 'pendiente'`, `init_point` y `pago_en_vuelo`.
  - No crear una segunda preferencia.

Esto evita el bloqueo permanente si el proceso muere entre el commit y la creación de la preferencia.

### 5.3. Carrera de cancelación durante la llamada HTTP

Secuencia:

1. Se crea la intención P1 y se inicia la llamada HTTP.
2. El usuario cancela P1.
3. La cancelación bloquea comercio, invalida P1, limpia el puntero y hace commit.
4. Vuelve la respuesta HTTP de MP.
5. El re-lock ve P1 `invalidada` y puntero `NULL`.
6. No se guarda `preference_id` ni `checkout_url`.
7. No se reactiva P1.
8. Se responde `409` con `estado = 'intencion_invalidada'`.

### 5.4. Carrera de reemplazo durante la llamada HTTP

Secuencia:

1. P1 tiene la llamada HTTP en curso.
2. P1 se invalida y se crea P2; el puntero pasa a P2.
3. Vuelve la respuesta HTTP de P1.
4. El re-lock ve P1 `invalidada` y puntero P2.
5. No se guarda la preferencia de P1.
6. P2 no se toca.
7. Se responde `409` con `estado = 'intencion_reemplazada'`.

### 5.5. Webhook: resolución inicial y orden de locks

1. El webhook recibe `data.id` y consulta `GET /v1/payments/{id}`.
2. Extrae `external_reference` (token).
3. Hace una lectura inicial **sin lock** de `suscripcion_pago_intenciones` por token para obtener `comercio_id`.
4. Esa lectura inicial no es fuente de verdad. Sólo sirve para saber qué comercio bloquear.
5. Abre transacción:
   - Toma un advisory lock transaccional por `provider + gateway_transaction_id` con `pg_advisory_xact_lock`.
   - Bloquea primero el comercio con `lockForUpdate`.
   - Vuelve a consultar la intención por token con `lockForUpdate`.
   - Revalida:
     - La intención existe.
     - `intencion.comercio_id === comercio.id`.
     - `intencion.token === status.referenceId`.
     - `comercio.pending_intent_id === intencion.id`.
6. Si la revalidación falla:
   - No se aplica.
   - Se clasifica como `superseded`, `pendiente_conciliacion` o incidente, según corresponda.
7. Si la revalidación pasa:
   - Se validan estado, importe, moneda y preferencia.
   - Antes de crear un pago, se busca un `PagoHuerfano` no resuelto por `provider + gateway_transaction_id`.
   - Si existe, no se crea un pago: se actualiza el huérfano con el estado/reverso más reciente, se registra `huerfano_existente` y se deriva a conciliación manual. Esto evita que un pago y un huérfano pendiente del mismo `provider + gateway_transaction_id` se cuenten dos veces.
   - Si no existe, se aplica o se deriva a conciliación según corresponda.

Si la lectura inicial no encuentra la intención:

- Antes de crear un huérfano, se busca un pago por `provider + gateway_transaction_id`.
- Si el pago existe, es de suscripción y pertenece al mismo comercio, no se crea huérfano: se actualiza el pago y su reverso según corresponda. Si el pago es de otro comercio, se registra incidente y se crea/actualiza un `PagoHuerfano` con `motivo = conflicto_comercio`; no se modifica ni se reasigna el pago. Si el pago es de otro dominio (venta/pedido), se registra incidente y no se crea huérfano ni se modifica el pago.
- Si no existe pago y el estado es `approved` o `refunded`, se crea un `PagoHuerfano` con payload sanitizado, hash y el motivo correspondiente. Si hay un reverso positivo, el huérfano se guarda con `status = 'refunded'` aunque el gateway informe `approved`. No se guarda el payload crudo.
- Si el pago está `pending`, se registra sólo un log; no se crea huérfano hasta que exista una aprobación o reverso.
- No se bloquea ningún comercio porque no se conoce.
- La unicidad `provider + gateway_transaction_id` protege contra duplicados.

Si la lectura inicial encuentra una intención pero el comercio ya no existe:

- Se registra incidente y huérfano.
- No se aplica.

### 5.6. Aprobación: orden obligatorio

`SuscripcionPagoService::procesarAprobado()`:

1. Recibe `PaymentStatusResponse` obtenido desde el gateway.
2. **Valida explícitamente `status->status === PaymentStatus::APPROVED` y `gatewayStatus === 'approved'`.** Si no, no aplica y delega a `procesarNoAprobado()`.
3. Abre transacción.
4. Toma un advisory lock transaccional por `provider + gateway_transaction_id`.
5. Bloquea el comercio.
6. Bloquea la intención.
7. Valida `comercio.pending_intent_id === intencion.id`.
8. Valida estado `pendiente`.
9. Valida vigencia con `date_approved` si existe; si no existe, con `now()` como fecha de procesamiento. Esa fecha no se persiste como `approved_at`.
10. Valida importe y moneda contra la intención usando `ImporteDecimal`; no usa `float`, no redondea y no convierte a través de `number_format`.
11. Valida `preference_id` si está disponible.
12. Si el pago existe y está `aplicado` al mismo comercio, registra el reverso si el payload lo informa y responde `ya_aplicado` sin volver a aplicar. Si existe aplicado a otro comercio, registra incidente, crea/actualiza un `PagoHuerfano` con `motivo = conflicto_comercio`, no reasigna y retorna.
13. Si no existe pago aplicado, verifica que no exista un `PagoHuerfano` no resuelto por `provider + gateway_transaction_id`. Si existe, no crea ni actualiza pago; actualiza el huérfano con el estado/reverso más reciente, registra `huerfano_existente` y retorna conciliación manual. Si existe pago no aplicado y además un huérfano no resuelto (dato legacy), actualiza el huérfano, registra incidente de duplicado y retorna sin actualizar el pago.
14. Sólo si no existe huérfano no resuelto, crea o actualiza el pago. Si es nuevo, inicializa `reversal_status = 'sin_reverso'`, `refunded_amount = 0.00`, `chargeback_amount = 0.00`, `reversed_amount_total = 0.00` y `reversal_overlap_status = 'no_aplica'` sólo si el gateway informa explícitamente ausencia de reverso: `refundedAmount = '0.00'` y `chargebackAmount = '0.00'`, o `reversedAmountTotal = '0.00'` sin ningún componente positivo. Si falta `refundedAmount` o `chargebackAmount` y no hay un total `0.00` que permita afirmar ausencia, inicializa `reversal_status = 'desconocido'` con importes `NULL`; no se interpreta `NULL` como cero. Si el pago existente está `superseded` o `pendiente_conciliacion`, se actualizan sólo estado/reverso; no se promueve a `aplicado` automáticamente. En un pago existente, un `0.00` explícito no borra un reverso positivo ya conocido: se conserva el máximo y, si el pago estaba `refunded`, no se degrada a `approved`. Si el pago ya existía y el payload trae un reverso positivo, se registra con `registrarReverso()` sin cambiar su conciliación.
15. Si todo es válido y el pago fue creado en el paso 14 (no existía previamente):
    - Si el payload informa un reverso positivo (`refundedAmount`, `chargebackAmount` o `reversedAmountTotal` mayor a cero), se registra con `registrarReverso()` en la misma transacción. El pago no se aplica automáticamente: queda `pendiente_conciliacion` con motivo `reverso_en_aprobacion`. Un reverso total tampoco se aplica. No se calcula período, no se extiende vencimiento, no se marca la intención `aprobada` y no se limpia el puntero; se hace commit y se retorna.
    - Si falta el dato de reembolso/contracargo (no hay un `0.00` explícito que permita afirmar ausencia de reverso), se registra `reversal_status = 'desconocido'` con importes `NULL`; el pago queda `pendiente_conciliacion` con motivo `reverso_sin_datos` y no se aplica. Tampoco se calcula período ni se extiende vencimiento.
    - Si el gateway informa explícitamente ausencia de reverso:
      - `conciliation_status = 'aplicado'`.
      - Calcula período.
      - Extiende vencimiento, activa comercio, actualiza plan si corresponde.
      - Marca intención `aprobada`.
      - Limpia `comercios.pending_intent_id` y `comercios.pending_plan_id`; `payments.pending_intent_id` se conserva para trazabilidad y para la unicidad de intención aplicada.
16. Si no es válido:
    - Si ya existe un pago `aplicado` para el mismo `provider + gateway_transaction_id`:
      - Mismo comercio: no se degrada; se registra incidente, se registra el reverso si el payload lo trae, se responde idempotente y se retorna.
      - Otro comercio: no se modifica el pago; se registra incidente, se crea/actualiza un `PagoHuerfano` con `motivo = conflicto_comercio` y se retorna.
    - No toca la suscripción.
    - Registra el pago como `superseded` o `pendiente_conciliacion` según la tabla de clasificación.
    - Si hay un reverso positivo, se registra con `registrarReverso()`; si faltan datos suficientes, queda `reversal_status = 'desconocido'` con importes `NULL`.
    - Si el gateway informa explícitamente ausencia de reverso y el pago no tiene un reverso positivo conocido, conserva/registra `reversal_status = 'sin_reverso'` con `0.00` en los tres importes y `reversal_overlap_status = 'no_aplica'`; si ya tenía un reverso positivo, no se borra.
17. Commit.

`date_approved`:

- Si viene: `approved_at = date_approved`.
- Si falta: `approved_at = NULL`, `metadata.fecha_aprobacion_no_disponible = true`.
- Nunca se usa `now()` como `approved_at`.
- Si falta `date_approved`, `now()` puede usarse sólo como fecha de procesamiento para calcular el período, nunca como fecha de aprobación persistida.

### 5.7. Clasificación de un pago aprobado

| Situación | Resultado | ¿Aplica? |
|---|---|---|
| Token válido, intención vigente, puntero coincide, importe/moneda/preferencia OK y ausencia de reverso explícita | `aplicado` | Sí |
| Token válido, intención vigente, puntero coincide, importe/moneda/preferencia OK, pero falta el dato de reembolso/contracargo | `pendiente_conciliacion`; motivo `reverso_sin_datos`; no aplica | No |
| Token desconocido o sin `external_reference` | `pagos_huerfanos` | No |
| Existe huérfano no resuelto para el mismo `provider + gateway_transaction_id` | No se crea pago; huérfano actualizado; `huerfano_existente` | No |
| Token existe, comercio conocido, pero intención no vigente/invalidada/expirada/reemplazada | `superseded` | No |
| Token existe, puntero coincide, pero falta importe/moneda o no coinciden | `pendiente_conciliacion` | No |
| Token existe, puntero coincide, `preference_id` no coincide | `pendiente_conciliacion` | No |
| Pago ya aplicado al mismo comercio | Idempotente `ya_aplicado`; si el payload trae reverso, se registra | No vuelve a aplicar |
| Pago aprobado con reverso informado antes de aplicar | Registra pago y reverso; `pendiente_conciliacion` con motivo `reverso_en_aprobacion`; no aplica | No |
| Pago existe aplicado a otro comercio | Incidente + huérfano de conflicto | No |
| Pago no aprobado inicial (`pending`, `rejected`, `cancelled`, `expired`) | No se aplica | No |
| Pago aplicado que luego pasa a `refunded`/`charged_back` | Se registra reverso; conserva `aplicado` y sus períodos | No se vuelve a aplicar |
| Pago aplicado que recibe reembolso parcial y contracargo | Se registra `reverso_combinado`; no se duplica el descuento; conserva `aplicado` | No se vuelve a aplicar |
| Pago `superseded`/`pendiente_conciliacion` que luego se reembolsa | Se registra reverso; conserva su conciliación | No |

### 5.8. P1 reemplazada por P2

1. P1 creada. Puntero = P1.
2. P1 se invalida por cancelación, expiración o nueva intención.
3. P1 pasa a `invalidada`, motivo `reemplazada_por_nueva_intencion`.
4. P2 se crea. Puntero = P2.
5. Llega un pago aprobado tardío de P1:
   - Token P1 resuelve la intención.
   - Comercio conocido.
   - Puntero actual = P2.
   - Se registra `superseded`, motivo `intencion_no_vigente`.
   - No se extiende el período.
   - No se toca P2.
   - P1 sigue invalidada.
6. Aunque P1 tuviera artificialmente `status = 'pendiente'` y `expires_at` futuro, el puntero P2 hace que igualmente sea `superseded`.
7. Un pago aprobado de P2 sí se aplica.

### 5.9. Cancelación, expiración y pagos no aprobados

- `cancelarPago`: invalida la intención vigente y limpia `comercios.pending_intent_id` y `comercios.pending_plan_id` si coinciden; no toca `payments.pending_intent_id`.
- Expiración: no se necesita cron obligatorio. El servicio valida estado y `expires_at`.
- Si una intención expirada sigue apuntada, una nueva generación la invalida y reemplaza.
- Webhook no aprobado:
  - `rejected`, `cancelled`, `expired`: si la intención es la vigente, se invalida y se limpia `comercios.pending_intent_id`; `payments.pending_intent_id` se conserva.
  - `pending`: no se toca nada.
  - `refunded`/`charged_back`: se registra el reverso según 7.2; no se revierte automáticamente la suscripción. Si un reembolso parcial y un contracargo llegan combinados, no se suman a ciegas: se usa `reversed_amount_total` o queda `solapamiento_desconocido`.

### 5.10. Pago manual

`PagoManualService`:

- Bloquea el comercio.
- Valida plan, precio e importe.
- Verifica idempotencia.
- Verifica duplicado de período **sólo contra pagos `aplicado`**.
- Crea el pago con `conciliation_status = 'aplicado'`, período, `reversal_status = 'sin_reverso'`, `refunded_amount = 0.00`, `chargeback_amount = 0.00`, `reversed_amount_total = 0.00` y `reversal_overlap_status = 'no_aplica'`.
- Invalida la intención vigente y limpia el puntero **dentro de la misma transacción**.
- Elimina la limpieza post-commit de cache.
- En reintento idempotente no invalida una intención nueva.

### 5.11. Resolución de huérfanos: contrato de servicio (sin UI)

B3.2 no implementa UI, rutas ni controlador de resolución. Documenta el contrato que consumirá una operación posterior.

Método:

```php
SuscripcionPagoService::resolverHuerfano(
    PagoHuerfano $huerfano,
    array $datos,
    User $admin
): Payment
```

`$datos` acepta únicamente:

- `comercio_id` (requerido).
- `intencion_id` (nullable; si el token resuelve una intención, debe coincidir).
- `payment_id` (nullable; sólo si ya existe un pago candidato).
- `motivo_resolucion` (requerido, string).
- `nota` (nullable, string, máximo 2000 caracteres; no debe contener PII, datos de tarjeta ni secretos).
- `confirmar_vinculacion_existente` (bool, default `false`).

No acepta importes, estados, fechas, moneda ni token desde el cliente. Esos datos se leen del huérfano, del pago existente y del gateway.

Antes de la validación 1 se exige `pagos.huerfanos.resolver`; sin permiso se aborta sin revelar si el huérfano existe. El permiso se vuelve a validar dentro de la transacción, después de los locks y antes de cualquier escritura.

Validaciones previas:

1. El huérfano existe. Si ya está resuelto, se aplica primero la rama de idempotencia: sin `payment_id` se devuelve `resolved_payment_id`; con `payment_id` igual se devuelve el pago; con `payment_id` distinto se aborta por conflicto. Si no está resuelto, continúa la validación.
2. `provider` y `gateway_transaction_id` son válidos; se re-consulta el pago al proveedor y se compara `id`. Si el huérfano y el gateway tienen `external_reference`, deben coincidir; si no, no se resuelve. `amount` y `currency` se comparan sólo si el huérfano los tiene; si faltan, se completan según la validación 9. El `status` debe ser compatible: mismo estado, o una evolución `approved` ↔ `refunded`/`charged_back` con reverso coherente. Si el estado actual es `pending`, `cancelled` o `rejected`, no se resuelve; se actualiza el huérfano y se deriva a conciliación.
3. El huérfano está `approved` o `refunded`; si está `pending`, no se resuelve.
4. Se revalida `pagos.huerfanos.resolver` dentro de la transacción, después de los locks y antes de cualquier escritura.
5. El comercio existe y está activo o suspendido; no se resuelve sobre un comercio borrado. Si el huérfano tiene `comercio_id`, debe coincidir con el `comercio_id` del input; si no, se aborta sin reasignar. Si el huérfano no tiene `comercio_id`, sólo un `Administrador Global` puede resolverlo. Si el admin no es `Administrador Global`, `comercio_id` debe coincidir con su propio comercio; si no, se aborta con 403.
6. Si hay `intencion_id`, la intención existe, pertenece al comercio y su token coincide con `external_reference` del huérfano cuando éste existe.
7. Si el `external_reference` resuelve una intención, se usa esa y el `intencion_id` del cliente, si viene, debe coincidir; no se acepta una intención distinta. Si el token no resuelve, se usa el `intencion_id` validado si vino; si no vino, se permite resolver con `resolved_intent_id = NULL` y motivo `sin_intencion`; no se inventa una intención.
8. Si el huérfano tiene importe/moneda y hay pago o intención, deben coincidir usando `ImporteDecimal`. Si no coinciden, no se resuelve.
9. Si el huérfano no tiene importe/moneda, se puede vincular sólo si el pago del proveedor se re-consulta y confirma el dato. En ese caso, el pago y el huérfano se completan con el importe/moneda confirmados dentro de la misma transacción. Si hay intención y ésta tiene importe/moneda, el dato confirmado por el gateway también debe coincidir con la intención; si no, no se resuelve. Si el pago existente ya tiene importe/moneda y no coincide con el gateway, se aborta; no se sobrescribe. Si no se puede confirmar, no se resuelve.
10. Si la re-consulta informa un reverso más reciente, se actualiza el huérfano (snapshots, estado y `reversal_source_updated_at`) antes de crear o vincular el pago; el pago copia esos datos. Si el huérfano está `refunded`/`charged_back` y su `reversal_status` es `sin_reverso` (dato legacy inconsistente), se normaliza a `desconocido` antes de copiar; no se crea un pago `refunded` con `sin_reverso`. Si el reverso es incoherente, no se resuelve y queda pendiente.
11. Si hay `payment_id`, el pago existe, es de tipo `Comercio`, pertenece al mismo comercio y coincide con `provider + gateway_transaction_id` del huérfano. Si pertenece a otro comercio o no coincide, se aborta. Si el pago tiene `pending_intent_id` no nulo y hay `intencion_id`, ambos deben coincidir; si no, se aborta.

Lock order:

1. Lectura inicial sin lock del huérfano para obtener `provider`, `gateway_transaction_id` y `external_reference`.
2. Abrir transacción.
3. Tomar un advisory lock transaccional por `provider + gateway_transaction_id`.
4. Bloquear `comercio`.
5. Bloquear `suscripcion_pago_intencion` si hay.
6. Bloquear el pago candidato por `provider + gateway_transaction_id` si existe.
7. Bloquear el `pago_huerfano` y revalidar `resolved_at`: si otro proceso lo resolvió, se aplica la rama de idempotencia (mismo pago) o se aborta por conflicto (pago distinto), sin crear ni actualizar nada.

El orden `advisory(provider+tx) → comercio → intención → pago → huérfano` es consistente con el webhook. El huérfano se bloquea último para evitar deadlocks con la creación de huérfanos.

Idempotencia y doble contabilización:

- Si el huérfano ya está resuelto:
  - Si `resolved_comercio_id` no coincide con el `comercio_id` del input, se aborta por conflicto; no se revela ni se reasigna el pago.
  - Se verifica que `resolved_payment_id` pertenezca a `resolved_comercio_id`; si no, se aborta por inconsistencia cross-tenant.
  - Si no se pasó `payment_id`, se devuelve `resolved_payment_id` sin crear ni actualizar nada.
  - Si `resolved_payment_id` coincide con el pago candidato, se devuelve el pago sin crear ni actualizar nada.
  - Si difiere, se aborta con conflicto; no se reasigna.
- Si el pago ya existe:
  - Si `confirmar_vinculacion_existente = false` y no se pasó `payment_id`, se aborta con `requiere_confirmacion`; no se vincula automáticamente.
  - Mismo comercio y confirmación válida: se vincula; no se crea otro; no se modifican importes, períodos ni conciliación. Si el pago no tenía reverso conocido (`reversal_status IS NULL`, `sin_reverso` o `desconocido` con importes nulos) y el huérfano sí trae datos, se copian los campos de reverso y se ajusta `status = 'refunded'` y `refunded_at` si faltaba. Si el pago ya tenía un reverso distinto, se aplica la regla de conflicto de reverso.
  - Otro comercio: se aborta; no se reasigna; se registra incidente y el huérfano sigue pendiente conservando su `motivo` de creación. El incidente referencia `conflicto_comercio`; no se sobrescribe el motivo del huérfano.
- Si el pago no existe:
  - Se crea con `provider`, `gateway_transaction_id`, `payable_type = Comercio`, `payable_id = comercio_id`, `amount`, `currency`, `status`, `pending_intent_id` si hay intención, `conciliation_status = 'pendiente_conciliacion'`, `conciliation_reason = 'resolucion_huerfano'`, períodos `NULL`, reversos copiados del huérfano y `approved_at` del huérfano si existe. Si el huérfano tiene un reverso positivo, el pago se crea con `status = 'refunded'` aunque el huérfano esté `approved`; el huérfano también se normaliza a `refunded`. Si el huérfano está `refunded`, `refunded_at` se toma de `reversal_source_updated_at` si existe; si no, de `received_at`; no se inventa una fecha de aprobación. Si el huérfano no tenía importe/moneda, se usan los valores confirmados por el gateway en la validación 9.
  - No se extiende la suscripción, no se cambia el plan y no se toca `comercios.pending_intent_id`.
  - Se usa `firstOrCreate` con `payments_provider_tx_unique`; si otro proceso crea el pago, se re-consulta, se revalida que pertenezca al mismo comercio y se vincula. Si pertenece a otro comercio, se aborta sin reasignar.
- El unique de `pagos_huerfanos.resolved_payment_id` impide que dos huérfanos apunten al mismo pago.
- Las métricas excluyen huérfanos resueltos y cuentan el pago una sola vez.

Actualización atómica del huérfano:

- `resolved_comercio_id`, `resolved_intent_id`, `resolved_payment_id`, `resolved_at = now()`, `resolved_by_id = admin.id`, `resolution_reason` y `resolution_note`.
- Si el huérfano tenía `amount`/`currency` nulos y el gateway los confirmó, se actualizan en el huérfano antes de marcar la resolución.
- `motivo` no se sobrescribe: conserva el motivo de creación.
- Todo ocurre en una sola transacción; si falla el pago o la auditoría, no se marca resuelto.

Conflictos:

- Pago existente en otro comercio: abortar, no reasignar, incidente, huérfano pendiente.
- Intención de otro comercio: abortar.
- Pago existente con `pending_intent_id` distinto de la intención resuelta: abortar.
- Token distinto: abortar.
- Importe o moneda distintos: abortar y derivar a conciliación.
- Pago existente `aplicado`: vincular; no se vuelve a aplicar ni se modifican períodos o conciliación. Si el huérfano trae un reverso que el pago no tenía (`reversal_status IS NULL`, `sin_reverso` o `desconocido` con importes nulos), se copia el reverso y se ajusta `status='refunded'`/`refunded_at`.
- Pago existente `superseded` o `pendiente_conciliacion`: vincular; no se modifican períodos ni conciliación. El reverso se copia sólo si el pago no tenía reverso conocido.
- Pago existente con reverso distinto: no sobrescribir; no se marca el huérfano como resuelto; se registra incidente y el reverso queda pendiente de conciliación.
- Pago ya vinculado a otro huérfano: abortar por el unique de `resolved_payment_id`; no reasignar.

Auditoría:

- `activity('pagos_huerfanos')->performedOn($huerfano)->causedBy($admin)->withProperties([...])->log('resolucion_huerfano')`.
- Propiedades: `huerfano_id`, `payment_id`, `comercio_id`, `intencion_id`, `motivo_resolucion`, `nota_presente`, `resultado` y estado anterior/posterior de `resolved_*`.
- `resolution_note` se guarda sólo en el huérfano; no se replica en logs ni auditoría. No se guarda payload, PII ni secretos en la auditoría. La nota es operativa y no debe contener PII, datos de tarjeta ni secretos.
- `resolved_by_id` y `resolved_at` son la fuente de verdad.
- La auditoría no se elimina con la purga de payload.

Resultado:

- Pago creado o vinculado.
- Huérfano resuelto.
- Suscripción no aplicada.
- Huérfano fuera de pendientes; pago contado una vez.

Fuera de alcance de esta operación: UI, rutas, controlador, menú, permisos de menú, aplicación automática de la suscripción y reverso automático.

## 6. Procedencia autoritativa de datos del gateway

| Dato | Fuente autoritativa | Regla |
|---|---|---|
| `payment_id` | `GET /v1/payments/{id}` → `id` | El `data.id` del webhook sólo sirve para consultar. No se usa como ID final. |
| `status` | `GET` → `status` | No se confía en el navegador ni en el query string. |
| `gateway_status` | `GET` → `status` crudo | Permite distinguir `refunded` de `charged_back`. |
| `status_detail` | `GET` → `status_detail` | Se guarda si existe. |
| `amount` | `GET` → `transaction_amount` | Se extrae como decimal canónico; no se usa el precio del plan, el importe del request ni `float`. |
| `currency` | `GET` → `currency_id` | No se hardcodea `ARS`. |
| `date_approved` | `GET` → `date_approved` | Si falta, `approved_at = NULL` y bandera. No se usa `now()`. |
| `date_last_updated` | `GET` → `date_last_updated` | Ordena snapshots de reverso; si falta, se usa `reversal_recorded_at` y se registra `orden_dudoso`. |
| `payment_method` | `GET` → `payment_method_id` | Se guarda si existe. |
| `external_reference` | `GET` → `external_reference` | Es el token de la intención. |
| `preference_id` | `GET` → `preference_id`, si existe | Si no viene, se usa el guardado al crear la preferencia. Nunca el navegador. |
| `metadata` | `GET` → `metadata` | Sólo secundaria. No define comercio ni plan. |
| `refunded_amount` | `GET` → `transaction_amount_refunded` | Snapshot acumulativo del total reembolsado; no se suma entre notificaciones. Si falta, no se inventa. |
| `chargeback_amount` | `GET` → campo de contracargo si existe | Snapshot acumulativo del total contracargado; si falta, no se asume el total. |
| `reversed_amount_total` | `GET` → total combinado de reverso, si existe | Sólo se usa si el gateway lo informa; si no, `NULL`. El solapamiento es desconocido sólo si ambos importes existen; si falta uno, el estado de solapamiento es `NULL`. |
| `comercio` | Intención resuelta por token | En `confirmarUpgrade`, además debe coincidir con el comercio autenticado. |
| `plan` | Intención | `request.plan_id` sólo se compara; no es fuente de verdad. |
| `tipo=plan` | Query string del webhook | Sólo enruta. No autoriza. |
| `payment_id` del navegador | Request del navegador | Es una pista para consultar MP. No es fuente de verdad. |
| `plan_id` del navegador | Request/back URL | No es fuente de verdad. Se compara contra la intención. |

Reglas:

- No se aplica un pago sólo por `external_reference`.
- Se verifica estado, importe, moneda, correlación de token y puntero.
- Si falta información indispensable para aplicar, se deriva a conciliación.
- No se inventan importes, monedas, fechas, comercios ni planes.
- Los importes se comparan como `ImporteDecimal`; no se usa `float`, `round()` ni `number_format()`.
- Si falta `date_approved`, se aplica sólo si el resto es válido, con `approved_at = NULL` y bandera.
- Si falta `preference_id`, no se bloquea: se registra `preferencia_no_verificada`. El token, importe, moneda y puntero siguen siendo obligatorios.
- Si falta el importe de un reverso, se marca `reversal_status = 'desconocido'` y queda pendiente de conciliación. No se calcula el neto como si el reverso fuera cero.
- `transaction_amount_refunded` y el importe de contracargo son snapshots, no incrementos. No se suman notificaciones sucesivas.
- Si reembolso y contracargo coexisten, ambos importes están y no hay total combinado, `reversed_amount_total = NULL`, `reversal_overlap_status = 'solapamiento_desconocido'` y el neto es parcial. No se suman a ciegas. Si falta uno de los dos importes, `reversal_overlap_status = NULL` y también se publica neto parcial con las cotas de 7.2.

### 6.1. Contrato `PaymentStatusResponse` a ampliar

Campos nuevos o explícitos:

| Campo | Tipo | Uso |
|---|---|---|
| `gatewayStatus` | string | Estado crudo del proveedor; distingue `refunded` de `charged_back`. |
| `statusDetail` | ?string | Detalle del estado. |
| `amount` | ?string | Importe de la transacción en decimal canónico de 2 decimales; reemplaza el `?float` existente. |
| `currency` | ?string | Moneda informada por el gateway. |
| `dateApproved` | ?CarbonImmutable | Fecha real de aprobación; si falta, `approved_at = NULL`. |
| `dateLastUpdated` | ?CarbonImmutable | `date_last_updated`; ordena snapshots de reverso. |
| `paymentMethod` | ?string | Método de pago informado. |
| `preferenceId` | ?string | Preferencia informada por el gateway, si existe. |
| `refundedAmount` | ?string | Snapshot acumulativo de `transaction_amount_refunded`, decimal canónico; nunca `float`. |

`MercadopagoGateway` debe mapear `status`, `status_detail`, `transaction_amount`, `currency_id`, `date_approved`, `date_last_updated`, `payment_method_id`, `preference_id`, `transaction_amount_refunded` y, si existe, el total combinado de reverso. Para `charged_back`, si no hay campo de importe, `chargebackAmount = NULL`; no se asume el total.

Ningún campo monetario de `PaymentStatusResponse` es `float`. Los valores se construyen como string decimal canónico y se convierten a `ImporteDecimal` una sola vez.

Compatibilidad con ventas/pedidos: `WebhookPayload`, `PaymentRecorder`, `PaymentConfirmationService` y `ViumiGateway` conservan su contrato legacy `?float` y no se modifican en B3.2. En ese borde, PHP convierte el string a `float` para los pagos de pedidos; esa conversión no se usa en suscripción, no participa de las comparaciones de B3.2 y queda fuera de alcance. El camino de suscripción no pasa por `WebhookPayload` ni por `PaymentRecorder`.

### 6.2. Representación monetaria exacta

Formato canónico:

- `^\d{1,10}\.\d{2}$`.
- Sin signo, sin separadores de miles, sin notación científica y sin espacios.
- Sin ceros a la izquierda innecesarios; `0` se representa `0.00`.
- Rango compatible con `decimal(12,2)`: `0.00` a `9999999999.99`.
- Se aceptan tokens de entrada como `123`, `123.4` o `123.45` y se normalizan por padding de ceros, nunca por redondeo. Un valor con más de 2 decimales se rechaza.
- Un valor negativo, fuera de rango, `NaN`, `INF` o no numérico se rechaza y se deriva a conciliación; no se corrige por aproximación.

`App\Support\ImporteDecimal`:

- Value object inmutable construido desde string canónico, string de base de datos o token decimal del gateway.
- `toCanonicalString()`: devuelve siempre 2 decimales.
- `toMinorUnits()`: devuelve `int` en centavos; se usa para comparar y sumar.
- `compare()`, `add()`, `subtract()`, `isZero()`, `isNegative()`: aritmética entera, sin `float`.
- `fromDatabase()`: acepta el string que devuelve el cast `decimal:2` de Eloquent.
- `fromGateway()`: exige que el adaptador haya preservado el token decimal como string. Si el cliente HTTP ya convirtió el JSON a `float`, el valor no se usa: se marca `amount = NULL` y se deriva a conciliación.
- `MercadopagoGateway` lee el body crudo o un parser que preserve números como strings. No usa `(float)`, `floatval()`, `number_format()` ni `round()` para importes.
- Las comparaciones de intención, transacción, reembolso y contracargo usan `compare()` o `toMinorUnits()`.
- Las sumas de métricas se hacen en unidades menores por moneda y se convierten a canónico sólo para presentación.
- La persistencia usa el string canónico; el cast `decimal:2` de Eloquent devuelve string y no se vuelve a convertir a `float`.
- Si un importe no se puede representar exactamente, no se redondea: se registra `monto_invalido` o `reverso_sin_datos` y queda pendiente de conciliación.

Pruebas de precisión obligatorias:

- `0.01`, `0.10`, `1.00`, `10.00`, `99.99`, `100.00`, `9999999999.99`.
- `0.29` + `0.01` = `0.30` usando unidades menores.
- `1.10` y `1.1` se normalizan al mismo canónico `1.10`.
- `2.675` se rechaza; no se redondea a `2.68`.
- `0.1 + 0.2` no se evalúa con `float`; se compara `10 + 20 = 30` centavos.
- Importe de intención `100.00` contra transacción `100.00` es igual; `100.00` contra `99.99` no lo es.
- Reembolso `33.33` + `33.33` = `66.66`; no se pierde un centavo.
- Valor máximo `9999999999.99` no desborda `int` de 64 bits en centavos.
- Valor `10000000000.00` se rechaza por exceder `decimal(12,2)`.

## 7. Métricas financieras y reversos

### 7.1. Definiciones

Sea `P` = pagos con `payable_type = Comercio` y `metadata.tipo = 'suscripcion'`.

Sea `H` = `pagos_huerfanos` con `resolved_at IS NULL` y sin un pago existente con el mismo `provider + gateway_transaction_id`. Un huérfano con pago existente es un duplicado legacy: no se suma en métricas y se registra incidente hasta que se resuelva.

| Métrica | Definición | ¿Incluye superseded? | ¿Extiende suscripción? |
|---|---|---|---|
| `renovaciones_aplicadas` | `P` con `conciliation_status='aplicado'` (aunque luego pase a `status='refunded'`), separado por origen online/manual | No | Sí |
| `ingreso_aplicado` | Suma bruta de `renovaciones_aplicadas`; no descuenta reversos | No | Sí |
| `pagos_aprobados_proveedor` | `P` con `provider='mercadopago'` y `status IN ('approved','refunded')`, cualquier conciliación y cualquier reverso | Sí | No |

| `importe_contracargado` | Suma de snapshots `chargeback_amount` conocidos en `P` y `H` con `status IN ('approved','refunded')`; métrica informativa, no se resta por separado | Sí | No |

Reglas:

- `superseded` no cuenta como renovación ni como ingreso aplicado.
- `superseded` sí cuenta en `pagos_aprobados_proveedor`, `pagos_pendientes_conciliacion`, `pagos_superseded`, `importe_bruto_aprobado` y `dinero_bruto_recibido_total`.
- Los pagos manuales cuentan en `renovaciones_aplicadas` e `ingreso_aplicado`, y se suman a `dinero_bruto_recibido_total`/`dinero_neto_recibido_total` como dinero recibido; no se suman a `pagos_aprobados_proveedor` ni a `importe_bruto_aprobado`, que son métricas de proveedor.
- Los huérfanos resueltos se excluyen de `pagos_huerfanos_pendientes` y pasan a contarse como pago. Así no hay doble conteo.
- Todas las métricas se agrupan por moneda. No se suman monedas distintas. Las sumas se hacen en unidades menores y se convierten a decimal canónico sólo al presentar.
- `mrr_estimado` sigue siendo una proyección desde planes y no se mezcla con dinero recibido.
- `importe_reembolsado` e `importe_contracargado` son informativos. Nunca se restan juntos: el único descuento es `importe_reversado_confirmado`.
- `importe_reversado_confirmado`, `neto_minimo` y `neto_maximo` incluyen `H` con `status IN ('approved','refunded')` y reverso; los huérfanos resueltos se cuentan como pago y no se duplican.
- Si un huérfano no resuelto coexiste con un pago del mismo `provider + gateway_transaction_id` (duplicado legacy), no entra en `H`: se registra incidente y se excluye de las métricas hasta que se resuelva. Si el huérfano trae un reverso que el pago no refleja, el pago se incluye en `pagos_con_reverso_pendiente` y el neto se marca `parcial`; el reverso no se descuenta del huérfano para evitar doble conteo y se copia al resolver.
- Si hay pagos u huérfanos pendientes con `reversal_status='desconocido'`, `reversal_status IS NULL` o `reversal_overlap_status='solapamiento_desconocido'`, `dinero_neto_recibido_total` se marca como `parcial` y se expone `pagos_con_reverso_pendiente`/`pagos_huerfanos_con_reverso_pendiente`. No se presenta un neto definitivo ni se interpreta `NULL` como cero.
- Si `importes_incompletos > 0`, `importe_bruto_aprobado`, `dinero_bruto_recibido_total`, `dinero_neto_recibido_total` y `dinero_neto_recibido_parcial` se marcan como `parcial`; no se publican `neto_minimo`/`neto_maximo`. Un `amount = NULL` no se suma como cero.
- Para pagos con reverso pendiente, se exponen `neto_minimo` y `neto_maximo` como cotas, nunca como neto definitivo. Las cotas cubren solapamiento desconocido y también importes de reverso faltantes.
- Un pago `aplicado` con reverso total sigue siendo una renovación aplicada y sigue en `ingreso_aplicado` (bruto), pero su aporte neto es cero. No se revierte la suscripción automáticamente.
- `ingreso_aplicado` es una métrica bruta de renovaciones. El dinero efectivamente retenido se lee en `dinero_neto_recibido_total`, que descuenta `reversed_amount_total`.

### 7.2. Reembolsos y contracargos

Semántica de los importes de Mercado Pago:

- `transaction_amount_refunded` es un snapshot acumulativo del total reembolsado del pago. No es incremental. Cada notificación reemplaza el snapshot si es mayor; no se suma entre notificaciones.
- El importe de contracargo, si el proveedor lo expone, se trata como snapshot acumulativo del total contracargado del pago. Si no existe campo de importe, `chargeback_amount = NULL` y no se asume el total.
- Reembolso y contracargo no se asumen independientes. Si ambos existen y el proveedor no informa un total combinado, el solapamiento es desconocido y no se calcula un neto definitivo.
- Un total combinado informado por el proveedor se usa sólo si es consistente: `>= max(refunded, chargeback)` y `<= refunded + chargeback` y `<= amount`.

Estados de reverso:

| Situación | `reversal_status` | `reversed_amount_total` | `reversal_overlap_status` |
|---|---|---|---|
| Sin reverso conocido | `sin_reverso` | `0.00` | `no_aplica` |
| Sólo reembolso parcial | `reembolso_parcial` | `refunded_amount` | `no_aplica` |
| Sólo reembolso total | `reembolso_total` | `refunded_amount` | `no_aplica` |
| Sólo contracargo | `contracargo` | `chargeback_amount` | `no_aplica` |
| Reembolso + contracargo, total combinado informado | `reverso_combinado` | total combinado | `total_combinado_informado` |
| Reembolso + contracargo, sin total combinado o total inconsistente | `reverso_combinado` | `NULL` | `solapamiento_desconocido` |
| Falta importe | `desconocido` | `NULL` | `NULL` si falta algún importe; `solapamiento_desconocido` sólo si ambos importes están y no hay total |

`registrarReverso()`:

1. Toma un advisory lock transaccional por `provider + gateway_transaction_id`.
2. Busca el pago por `provider + gateway_transaction_id` con lock.
3. Si no existe, busca un `PagoHuerfano` no resuelto por `provider + gateway_transaction_id`; si existe, lo actualiza; si no, crea uno con los datos del reverso, payload sanitizado y hash.
4. Si existe pago, valida `amount`, `currency` y `gateway_transaction_id`. Si el llamador conoce el comercio/intención por token y el pago pertenece a otro comercio, no se modifica: se registra incidente y se crea/actualiza el huérfano con `motivo = conflicto_comercio`.
5. Convierte los importes del gateway a `ImporteDecimal`; si no son exactos, marca `reverso_sin_datos` y no inventa.
6. Calcula snapshots monotónicos:
   - `refunded_amount = max(refunded_actual, refunded_entrante)`.
   - `chargeback_amount = max(chargeback_actual, chargeback_entrante)`.
   - Un `NULL` entrante no borra un valor conocido; un `NULL` actual se completa con el entrante. Nunca se reemplaza un importe conocido por `NULL`.
7. Si `reversal_source_updated_at` existe y es menor al guardado:
   - Si el snapshot entrante no supera el actual, se descarta y se registra `reverso_fuera_de_orden`.
   - Si el snapshot entrante supera el actual, se conserva el máximo, no se retrocede la fecha guardada y se registra `reverso_fuera_de_orden` para revisión; no se pierde el reverso mayor.
   Si no existe fecha, se aplica el máximo y se registra `orden_dudoso`.
8. Clasifica:
   - Sin reverso: `sin_reverso` sólo si el gateway no informa `refunded`/`charged_back` y se cumple una de estas dos condiciones: `refunded_amount = 0.00` y `chargeback_amount = 0.00` son conocidos, o `reversed_amount_total = 0.00` sin ningún componente positivo. Se persisten los tres importes en `0.00` y `reversal_overlap_status = 'no_aplica'`. Si el total informado es mayor a `0.00` y no hay componentes positivos, el dato es inconsistente y queda `desconocido`. Si el gateway informa `refunded`/`charged_back` pero los importes conocidos son `0.00`, no se clasifica `sin_reverso`: queda `desconocido` y se registra incidente.
   - Sólo reembolso: `reembolso_parcial` si `refunded > 0`, `chargeback = 0.00` conocido y `refunded < amount`; `reembolso_total` si `refunded = amount`. Si `chargeback` es `NULL`, no se clasifica como sólo reembolso.
   - Si `amount` es `NULL` y sólo hay reembolso, no se puede distinguir parcial de total: `desconocido`, `reversed_amount_total = NULL` y `reversal_overlap_status = NULL`.
   - Sólo contracargo: `contracargo` si `chargeback > 0` y `refunded = 0.00` conocido; si `refunded` es `NULL`, no se clasifica como contracargo.
   - Ambos: `reverso_combinado` si `refunded > 0` y `chargeback > 0`.
   - Un `0.00` no cuenta como componente positivo de reverso. Si el total combinado es mayor a `0.00` y no hay ningún componente positivo, el dato es inconsistente: `desconocido` con total `NULL`.
   - Sin datos suficientes, o si falta el cero explícito del componente que se supone ausente: `desconocido`.
9. Calcula `reversed_amount_total` y `reversal_overlap_status`:
   - Sin reverso: `0.00` y `no_aplica`.
   - Sólo reembolso: igual a `refunded_amount` y `no_aplica`.
   - Sólo contracargo: igual a `chargeback_amount` y `no_aplica`.
   - Ambos con total combinado: el total informado, validado contra `max`, suma y `amount`, y `total_combinado_informado`.
   - Ambos sin total combinado o con total inconsistente: `NULL` y `solapamiento_desconocido`; el total inválido se descarta y se registra incidente.
   - Un total combinado sin ambos componentes (reembolso y contracargo) no se usa: si hay un solo componente, se clasifica por ese componente con `no_aplica`; si no hay ninguno, el estado queda `desconocido` con total `NULL`.
   - Si `refunded_amount > amount` o `chargeback_amount > amount`, no se persiste el valor inválido: se conserva el snapshot válido anterior o `NULL`, se registra `monto_no_coincide` y se deriva a conciliación. Si no queda ningún snapshot válido, `reversal_status='desconocido'` y `reversed_amount_total=NULL`; nunca se viola el CHECK.
10. Actualiza `reversal_status`, `reversal_overlap_status`, `reversed_amount_total` y `reversal_source_updated_at`; en `payments` actualiza `reversal_recorded_at` y en `pagos_huerfanos` actualiza `last_received_at` como marca de registro.
11. Marca `status = 'refunded'` y `refunded_at` si no estaba seteado sólo cuando el gateway informa `refunded`/`charged_back` o cuando hay un reverso positivo (`refunded_amount > 0` o `chargeback_amount > 0`). Un `sin_reverso` explícito no cambia el estado del pago; un `desconocido` sin importes positivos tampoco lo cambia. Si el gateway ya informa `refunded`/`charged_back`, el estado se persiste como `refunded` aunque falte el importe del reverso.
12. No cambia `conciliation_status` si el pago ya estaba `aplicado`; conserva sus períodos.
13. No cambia plan, vencimiento ni estado del comercio.
14. No revierte automáticamente la suscripción.

Duplicados y fuera de orden:

- Notificación duplicada con los mismos importes: no-op; no duplica filas ni suma importes.
- Notificación con snapshot menor y `date_last_updated` menor: se ignora y se registra anomalía.
- Notificación con snapshot menor pero sin fecha: no se reduce el snapshot; se conserva el máximo y se registra `orden_dudoso`.
- Notificación con fecha mayor pero snapshot menor: tampoco se reduce; se conserva el máximo y se registra `reverso_fuera_de_orden` para revisión.
- Notificación con total combinado menor: no se reduce automáticamente; se registra anomalía y queda pendiente de conciliación.
- Reembolso después de contracargo y contracargo después de reembolso producen el mismo estado final para los mismos snapshots; el orden de llegada no duplica importes.
- Si `refunded + chargeback > amount` y no hay total combinado, se permite el estado `reverso_combinado` con solapamiento desconocido. No se rechaza por suma; se rechaza sólo si un importe individual supera `amount`.

Cálculo de neto:

Sea `A = amount`, `R = refunded_amount`, `C = chargeback_amount`, `T = reversed_amount_total`.

- Si `T` no es `NULL`: `neto = A - T`. El total ya fue validado contra `max(R,C)`, `R + C` y `A`.
- Si `T` es `NULL`: no hay neto definitivo. Se publica `dinero_neto_recibido_parcial` y, si `A` existe, las cotas `neto_minimo`/`neto_maximo`.
- Si `A` es `NULL`: no se calculan cotas numéricas; el pago queda pendiente y el neto agregado se marca `parcial`. No se interpreta `NULL` como cero.

Cotas de reverso pendiente:

| Datos disponibles | Cota mínima de reverso (`reverso_min`) | Cota máxima de reverso (`reverso_max`) |
|---|---|---|
| `T` conocido | `T` | `T` |
| `R` y `C` conocidos, `T = NULL` | `max(R,C)` | `min(A, R + C)` |
| Sólo `R` conocido | `R` | `A` |
| Sólo `C` conocido | `C` | `A` |
| Ninguno conocido | `0.00` | `A` |

- `neto_maximo = A - reverso_min`: asume el menor reverso posible.
- `neto_minimo = A - reverso_max`: asume el mayor reverso posible.
- Si un importe conocido supera `A`, no se calculan cotas; se deriva a conciliación.
- Las cotas agregadas restan primero `importe_reversado_confirmado` y luego suman `reverso_min` o `reverso_max` de cada pago/huérfano pendiente.
- Las cotas se etiquetan como rango, nunca como “dinero neto recibido”.
- No se resta `refunded_amount + chargeback_amount` cuando ambos existen sin total combinado.
- No se automatiza la revocación de la suscripción. La decisión manual queda para B3.3.

| SEC08 | Admin con permiso lee payload | Permitido y auditado con usuario, huérfano y acción |
| SEC09 | Huérfano pendiente con payload que supera `retention_pending_days` | Purga de payload; metadatos y hash permanecen |
| SEC10 | Huérfano resuelto con payload que supera `retention_resolved_days` | Purga de payload; `resolved_*` y auditoría permanecen |
| SEC11 | Purga ejecutada dos veces | Idempotente; no falla ni borra auditoría |
| SEC12 | Intento de exportar payloads | Denegado; no hay endpoint de exportación |
| SEC13 | Pago de suscripción con respuesta MP | No se persiste el body crudo en `payments.gateway_response`/`gateway_request`; sólo campos allowlisted |

### 10.14. Contrato de resolución de huérfanos

| ID | Escenario | Resultado esperado |
|---|---|---|
| O01 | Resolver huérfano aprobado con intención válida | Crea pago `pendiente_conciliacion`, vincula `resolved_*`, no aplica suscripción |
| O02 | Resolver dos veces el mismo huérfano | Idempotente; devuelve el mismo pago; no duplica |
| O03 | Huérfano ya resuelto a otro pago | Conflicto; no reasigna |
| O04 | Pago existente mismo comercio `aplicado` | Vincula; no vuelve a aplicar; no cambia períodos/conciliación; copia reverso si falta |
| O05 | Pago existente mismo comercio `superseded` | Vincula; no crea otro; no cambia períodos/conciliación; copia reverso si falta |
| O06 | Pago existente en otro comercio | Aborta; no reasigna; incidente; huérfano pendiente |
| O07 | Intención de otro comercio | Aborta; no resuelve |
| O08 | Token del huérfano distinto al de la intención | Aborta; no resuelve |
| O09 | Importe o moneda distintos | Aborta; deriva a conciliación |
| O10 | Huérfano sin importe/moneda y sin confirmación del gateway | Aborta; no inventa |
| O11 | Huérfano con reembolso o contracargo | Crea pago con reverso; no aplica suscripción |
| O12 | Resolución concurrente de dos admins | Uno gana; el otro es idempotente o conflicto; un solo pago |
| O13 | Webhook concurrente con resolución | Advisory lock y unique de transacción; un solo registro (pago u huérfano); sin doble contabilización |
| O14 | Rollback al crear pago | Huérfano sigue pendiente; no se setean `resolved_*` |
| O15 | Auditoría de resolución | Registra admin, motivo, `nota_presente`, pago y estado anterior/posterior; sin PII |
| O16 | Usuario sin `pagos.huerfanos.resolver` | Denegado |
| O17 | Métricas después de resolver | Huérfano sale de pendientes; pago cuenta una vez |
| O18 | Resolución sin UI | No hay ruta, controlador, vista ni menú; sólo servicio y tests |
| O19 | Pago ya vinculado a otro huérfano | Aborta por unique de `resolved_payment_id`; no reasigna |
| O20 | Pago existente sin `confirmar_vinculacion_existente` | Aborta con `requiere_confirmacion`; no vincula |
| O21 | Gateway evoluciona de `approved` a `refunded`/`charged_back` | Resuelve con el reverso actualizado; no exige igualdad literal de estado |
| O22 | Gateway regresa a `pending`/`cancelled`/`rejected` | No resuelve; actualiza el huérfano y deriva a conciliación |

## 11. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| La FK compuesta de `payments` depende de `payable_id = comercio_id` | Check de `payable_type`, tests y documentación. Si cambia el modelo polimórfico, se revisa la FK. |
| FK circular `comercios` ↔ `intenciones` | Orden de migración/rollback documentado y probado. |
| `ON DELETE RESTRICT` bloquea limpiezas | No hay endpoints de borrado; se prioriza auditoría. |
| Divergencia `pending_intent_id` / `pending_plan_id` | El puntero es autoritativo. `pending_plan_id` es compatibilidad. Tests G07. |
| Preferencia remota creada en una carrera perdida | No se cancela remotamente; su token queda invalidado. Un pago será `superseded` o `pendiente_conciliacion`. |
| Intención pendiente sin preferencia por caída del proceso | Ventana de timeout y invalidación por `timeout_preferencia`. |
| Pago con ID de otro comercio | Unique + detección + incidente + huérfano de conflicto. No se reasigna. |
| Doble conteo de huérfanos resueltos | Se excluyen de huérfanos al setear `resolved_at`; pasan a pagos. Test F06. |
| Pago y huérfano no resuelto del mismo `provider + tx` | El webhook no crea pago si existe huérfano; `H` excluye duplicados legacy; incidente. Tests A17/H16/H17. |
| Carrera entre creación de pago y huérfano | Advisory lock transaccional por `provider + tx` en webhook, aprobación, reverso y resolución. Test H18. |
| Reverso sin importe | `reversal_status='desconocido'`; neto parcial; no se inventa. |
| Reverso automático de suscripción | Prohibido en B3.2. Sólo se registra y se muestra. |
| Datos legacy con moneda/fecha inventadas | Se documentan como limitación histórica; no se corrigen por suposición. |
| MP no devuelve `preference_id` | Se usa el guardado al crear la preferencia. Si no hay, se marca `preferencia_no_verificada`; no se bloquea. |
| Payload de huérfanos con PII | Allowlist sanitizada, cifrado `encrypted:array`, acceso sólo admin global con permisos, hash no reversible y purga programada. |
| Falla al persistir `preference_id` después de crear la preferencia | El token sigue siendo válido; el pago se resuelve por token, importe, moneda y puntero. |
| Harness de tests con FKs compuestas | Se verifica truncate/reseed y orden de tablas. |
| CHECK de períodos sobre datos legacy | El backfill valida y marca `pendiente_conciliacion` si falta período; no inventa. |
| `float` o JSON decodificado con pérdida de precisión | `ImporteDecimal`, extracción de decimales como string y pruebas PM01-PM10. Si no se preserva el token, importe `NULL` y conciliación. |
| MP no informa total combinado de reembolso + contracargo | `reversed_amount_total = NULL`, `solapamiento_desconocido`, neto parcial y cotas; nunca se suma a ciegas. |
| Reembolso y contracargo se solapan | No se suman; se usa total combinado si existe; si no, rango mínimo/máximo y conciliación. |
| Notificaciones de reverso fuera de orden | Snapshot máximo, `date_last_updated`, registro de anomalía y no reducción automática. |
| Resolución de huérfanos sin UI | Contrato de servicio probado, sin rutas ni controlador; la operación queda lista para una UI posterior. |
| Resolución concurrente o cross-tenant | Orden de locks, unique de transacción, unique de `resolved_payment_id`, aborto sin reasignación y auditoría. |
| Purga elimina payload necesario para investigar | Ventana de 180/90 días, hash y auditoría persistentes; el dato crudo se re-consulta al proveedor si hace falta. |

## 12. Criterios de aceptación

1. Ningún pago puede aplicar si `comercios.pending_intent_id` no coincide con la intención.
2. La comparación del puntero se hace dentro de la transacción, después de los locks.
3. Una intención invalidada, expirada o reemplazada nunca acredita una suscripción, aunque `status` y `expires_at` parezcan válidos.
4. P1 reemplazada por P2 queda cubierta por pruebas, incluyendo P1 con estado artificialmente `pendiente`.
5. Las FKs compuestas garantizan que la intención pertenezca al mismo comercio, sin trigger.
6. `comercios.pending_intent_id` tiene migración explícita, FK, índice, comportamiento de borrado y recuperación documentados.
7. `pagos_huerfanos` cumple unicidad, payload sanitizado y cifrado, hash, fecha, motivo, proveedor, duplicados, vinculación posterior, retención y aislamiento. No existe payload crudo.
8. `payments` tiene unicidad real por `provider + gateway_transaction_id` y el caso cross-tenant está definido.
9. La creación de preferencias re-lockea comercio e intención y descarta la preferencia si la intención dejó de ser vigente.
10. El webhook bloquea primero comercio y luego intención, y revalida token/comercio/puntero.
11. Las métricas distinguen renovaciones aplicadas, aprobados por proveedor, pendientes de conciliación y superseded.
12. Un `superseded` no cuenta como renovación ni ingreso aplicado, pero sí aparece en dinero bruto recibido.
13. Se distinguen importe bruto aprobado, importe reembolsado, importe contracargado, importe reversado confirmado y dinero neto recibido. Sólo `reversed_amount_total` se resta del bruto.
14. Si faltan datos de reverso o el solapamiento reembolso/contracargo es desconocido, queda pendiente de conciliación, sin inventar importes ni presentar un neto definitivo.
15. No se automatizan reversos de suscripción en B3.2. Un pago aplicado que pasa a `refunded` conserva `conciliation_status='aplicado'`, sus períodos y su condición de renovación; sólo se reduce el neto.
16. Un pago `aplicado` tiene `period_start` y `period_end`; `period_start <= period_end`. El CHECK admite `status='approved'` o `status='refunded'` para un pago aplicado.
17. `superseded` y `pendiente_conciliacion` no tienen períodos aplicados.
18. Los pagos de ventas y pedidos conservan `conciliation_status = NULL`.
19. `procesarAprobado()` valida explícitamente `approved`.
20. Si falta `date_approved`, `approved_at = NULL` y se registra la bandera; no se usa `now()` como fecha de aprobación.
21. La procedencia de cada dato del gateway está documentada; no se confía en el navegador ni sólo en `external_reference`.
22. No se inventan datos ausentes: se guarda `NULL` o se deriva a conciliación.
23. La nomenclatura es consistente con `SuscripcionPagoIntencion`.
24. Las migraciones son recuperables ante ejecuciones parciales.
25. La matriz de pruebas se implementa y la regresión B3/B3.1 pasa.
26. No se modifican precios, duraciones, cobros reales, integración real con MP, B4 ni B1-B10.
27. Ningún importe monetario del camino de suscripción se representa con `float` en `PaymentStatusResponse`, `SuscripcionPagoService`, `PagoManualService`, comparaciones ni métricas. La compatibilidad legacy de ventas/pedidos conserva `?float` y queda fuera de B3.2.
28. Los importes se normalizan a `decimal(12,2)` mediante `ImporteDecimal`; no hay redondeos implícitos ni conversiones inexactas.
29. Reembolso y contracargo combinados se calculan con snapshots y `reversed_amount_total`; no se descuenta dos veces el mismo importe.
30. Si no hay total combinado, el pago queda con `solapamiento_desconocido`, neto parcial y cotas; no se inventa un neto.
31. Los payloads de huérfanos se guardan sólo con allowlist sanitizada y cifrada; no se persisten PII, tarjetas, tokens ni headers.
32. El acceso a payloads requiere permisos de admin global y queda auditado; la retención y la purga están definidas.
33. `resolverHuerfano()` valida proveedor, transacción, comercio e intención, y crea o vincula el pago de forma idempotente.
34. La resolución actualiza `resolved_*` atómicamente, evita doble contabilización y no reasigna pagos cross-tenant.
35. La resolución deja auditoría de quién, cuándo, por qué y sobre qué pago; no aplica la suscripción.
36. No se crea un pago si existe un huérfano no resuelto del mismo `provider + gateway_transaction_id`; los duplicados legacy se excluyen de métricas y se marcan como incidente.
37. La UI, rutas y controlador de resolución siguen fuera de alcance; sólo se implementa y prueba el contrato de servicio.

## 14. Observaciones y limitaciones conocidas

No hay observaciones bloqueantes. Quedan limitaciones conocidas, manejadas explícitamente:

1. **Mercado Pago puede no devolver `preference_id` en la respuesta del pago.**
   - Se usa el `preference_id` guardado al crear la preferencia.
   - Si no hay dato, se marca `preferencia_no_verificada`; no se bloquea si token, importe, moneda y puntero coinciden.

2. **Mercado Pago puede no informar el importe exacto de un contracargo.**
   - Se marca `reversal_status='desconocido'` y `reversed_amount_total = NULL`.
   - El pago queda en `pagos_con_reverso_pendiente`.
   - Si `amount` y `refunded_amount` están disponibles, las cotas son `neto_minimo = 0.00` y `neto_maximo = amount - refunded_amount`; si falta `amount`, no se publican cotas.
   - El neto se muestra como parcial; no se inventa el importe.

3. **Datos legacy sin fecha real de aprobación, moneda o reverso.**
   - No se reconstruyen por suposición.
   - Se marcan como legacy o pendientes de conciliación.

4. **Preferencias remotas creadas en una carrera perdida.**
   - No se cancelan remotamente por decisión de alcance.
   - Su token queda invalidado localmente; un pago posterior será `superseded` o `pendiente_conciliacion`.

5. **Cambios futuros en la API de Mercado Pago.**
   - El mapeo de campos debe revisarse si MP cambia nombres o deja de enviar datos.
   - El diseño ya contempla `NULL` + conciliación.

6. **Mercado Pago puede no informar un total combinado de reembolso + contracargo.**
   - Se marca `reversal_overlap_status='solapamiento_desconocido'`.
   - `reversed_amount_total = NULL`; no se suman los importes.
   - Se publica neto parcial y cotas `neto_minimo`/`neto_maximo`; no se presenta un neto definitivo.

7. **Mercado Pago puede no informar el importe de contracargo.**
   - `chargeback_amount = NULL`, `reversed_amount_total = NULL` y `reversal_status='desconocido'`.
   - El pago queda en `pagos_con_reverso_pendiente`; no se asume el total.
   - Las cotas se calculan con la tabla de 7.2; si falta `amount`, no se publican.

8. **El payload crudo no se conserva.**
   - Se guarda sólo allowlist sanitizada, cifrada, más `payload_hash` SHA-256.
   - Si una investigación requiere el crudo, se solicita al proveedor o a logs externos con el proceso correspondiente; no se guarda por defecto.

9. **La extracción exacta de decimales puede fallar si el cliente HTTP ya convirtió el JSON a `float`.**
   - El adaptador debe preservar el token decimal como string.
   - Si no puede, el importe queda `NULL` y el pago se deriva a conciliación; nunca se redondea.

10. **La resolución de huérfanos no tiene UI en B3.2.**
    - Se documenta y prueba el contrato de servicio.
    - La UI, rutas y controlador quedan para una fase posterior.

## 15. Veredicto

**Aprobable para BUILD B3.2.**

El plan incorpora las diez observaciones, mantiene el alcance y no deja contradicciones conocidas entre estados, restricciones, migraciones y métricas. La precisión monetaria queda resuelta con `ImporteDecimal`; los reversos combinados se calculan con snapshots y `reversed_amount_total`, y cuando falta el total combinado se marcan como solapamiento desconocido con neto parcial y cotas, sin sumar a ciegas. Los payloads de huérfanos se guardan sanitizados, cifrados, con hash, acceso autorizado y purga. La resolución de huérfanos queda documentada como contrato de servicio idempotente, atómico, auditable y sin UI.

No quedan escenarios monetarios sin política: los casos sin datos del proveedor se derivan a conciliación y nunca se presentan como neto definitivo. No se implementó código, no se crearon ni modificaron migraciones, no se modificó la base de datos y no se ejecutaron pruebas que modifiquen datos.

Queda a la espera de aprobación explícita para iniciar BUILD B3.2.
